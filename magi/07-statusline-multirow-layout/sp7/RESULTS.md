## 3. 結論（實測後填，供寫回 `PLAN.md` D2）

### 3.1 原地更新是否安全

**安全（Chromium 系實測）**：「更新既有 option＋插入新 option 於固定尾項
之前」不搬焦點、不跳捲動、選取值不漂移（value 錨定，selectedIndex 隨插入
自然位移但顯示值正確）——含「變更提交同一刻全體更新」情境（下拉內選
「新增一列」觸發）亦正常。**T5.4 採用原地更新，無需額外防護。**

### 3.2 若不安全，需何種防護

原地更新路徑本身無需防護。但**「新增一列」的觸發機制需要防護**（見 §4
發現 2）——防護方式經使用者裁決＝把觸發整個移出 select（獨立按鈕），
而非在 select 內做鍵盤攔截。

### 3.3 對 D2「列選擇 UI」段落的回寫建議

已回寫（2026-07-11，PLAN.md D2「列選擇 UI」＋「從空白建多列」流程＋
Spikes S7 條目三處）：(1) select 僅枚舉使用中列、維持原地更新；
(2) 「新增一列」移出 select、改每段 select 旁獨立按鈕（語意＝把本段
移至新的一列）；(3) Firefox 未測註記。

## 4. 矩陣外新發現

1. **repro 儀表觀察者效應（已修，見 TESTING.md 補記 2）**：事件 log 面板
   高度增長造成的下拉自關——與 option 更新無關，修復後未再現。
2. **重大發現：閉合 select 的鍵盤導航逐按即提交 → 「新增一列」option
   會被無限誤觸**（Windows/Chromium）：Tab 至 select（不開下拉）按 ↓，
   每按一下立即發 `change`；行至「新增一列」即觸發建列，且新列 option
   插於其前、本段又指到新列（倒數第二項），再按 ↓ 又觸發——按住 ↓＝
   連鎖建列（實測 log：update #4–#7、rowCount 7→10 於 2 秒內）。
   **使用者裁決（2026-07-11）**：「新增一列」移出 select 改獨立按鈕
   （根治，勝過依賴 popup 開合偵測的脆弱鍵盤攔截）。已回寫 PLAN D2。
3. **閉合模式無「反白」態**（2.4 之解）：「反白不提交」僅存在於下拉
   展開時；閉合模式每按必提交。原設計「反白停在新增一列被擠位」邊角
   案在閉合模式不存在，開下拉情境未另測——發現 2 的裁決（移出 select）
   使該邊角案整體失效（option 清單中不再有「新增一列」）。
