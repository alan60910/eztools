## 3. 結論

### 3.1 列首 trim 行為

**Claude Code 會 trim 列首空白，空格與 tab 一律剝除**（case3：4sp／tab／
8sp 三種縮排列全部與無縮排基準列齊頭）。對 padding 契約的約束：
- 多列引擎**不得依賴列首空白**做縮排或對齊；「列首縮排」設計不可行，
  若未來需要縮排需改用非空白字元。
- 現行引擎輸出各列首段前本就無空白（padding 為段間／段尾語意），
  現行契約**不受影響**；此結論落為 PLAN 引擎契約節的禁止事項註記，
  防未來設計誤踩。
- 列內（非列首）空白渲染正常（case1／case2 段間空白未被合併或剝除）。

### 3.2 行尾契約裁決建議

**無尾隨換行與有尾隨換行渲染等價**（case1 vs case5：同樣 3 列、無多餘
空列、無任何可見差異）。裁決建議：**維持現行「無尾隨換行」契約**——
bash `printf '%s'`／ps1 `[Console]::Out.Write($out)`／oracle
`rows.map(joinRow).join('\n')` 三處皆不變，PLAN Open Q1 的備援分支
（三處同步加單一 LF）**不啟用**。T1.2 據此落地＝無程式碼變更，僅在
PLAN 引擎契約節記錄 S3 裁決完成。（補記：本對照係於 §4-A 腳本 bug
存在下取得——兩案輸出同等腐化仍渲染一致，結構等價證據成立；BOM
修復版 case1／case5 可選擇性重測補帶色確證。）

### 3.3 列數上限與截斷行為

**12 列全數渲染，未觸及任何列數上限**（case2 標號 row 01–row 12 完整
依序呈現）。上限若存在也 ≥12，足以支撐產品「列數無上限」敘事的實用
範圍；本結論**不需變更契約**。超寬列行為（case4）：單列於終端右緣
截斷並以 `…` 收尾，不自動換行、不影響後續列的渲染——多列引擎無需
為超寬列做防禦性處理。

## 4. 矩陣外新發現（影響契約，依 T1.2 協定先回報使用者再更新 PLAN）

### 4-A. ANSI 滲碼第一根因：spike 腳本自身 bug（已修復，非 Claude Code 行為）

**根因（2026-07-11 本機差分診斷確立）**：spike `.ps1` 原以「UTF-8 無 BOM
＋中文註解」儲存；Windows PowerShell 5.1（TESTING.md 建議接線 `powershell
-File`）對無 BOM 檔一律以 ANSI（本機 CP950）解析，中文註解的 UTF-8 位元組
被誤讀為 DBCS、其尾位元組吞掉換行，導致註解區塊後**第一行程式碼被併入註解
而未執行**——case1／case5 的 `$e = [char]27` 沒跑（`$e` 空字串→ESC 全數
消失、`[1m` 等以字面滲出）；case3 的 `$row1` 沒跑（基準列 `[0sp]baseline`
變空列——截圖少一列是這個 bug，不是 Claude Code 砍列）。

**證據鏈**：PS 5.1 直跑原檔 → stdout 無 `033`；同檔前置 BOM → `033` 完好；
pwsh 7（預設 UTF-8 讀檔）→ 一直正常（developer 當時只用 pwsh 驗證所以漏掉）。
使用者現役 statusline（同為 5.1 接線）有色彩，係因該檔含 BOM。

**修復（2026-07-11）**：全部 6 個 `.ps1`（含新增 case6）前置 UTF-8 BOM；
修復後 PS 5.1 輸出與 bash 版逐位元組一致（cmp 全過）、case5＝case1＋LF
對照性質保持。**對照組結論影響**：§3.1 trim、§3.3 列數與截斷結論不受
影響（od 證實前導空白確實有送達、12 列內容完整）；§3.2 行尾等價結論之
「結構等價」證據仍立（兩案同等腐化下渲染仍一致），修復版 case1／case5
可選擇性重測以取得帶色確證。

### 4-C. Claude Code statusline 僅支援基本 16 色 SGR（官方文件＋issues；待真機 case6 確證）

官方文件（code.claude.com/docs statusline）僅示範基本色；GitHub issues
證實：**256 色（`38;5;n`／`48;5;n`）與 truecolor（`38;2;r;g;b`）不支援、
會以字面文字滲出**（#16790、#6466），且**分開碼鏈可能失效、需合併**
（`\e[42;30m` 可用、`\e[42m\e[30m` 失效，#6466）；另有 statusline 一律
套 dimColor 蓋色的已知問題（#42382）。

**產品衝擊**：`color.ts` 的 `ColorSpec` 三態＝default／**ansi256**／
**truecolor**——**沒有 16 色軌**，若文件屬實則產品現行全部著色輸出
落在不支援形式上。

**✅ 真機確證結果（2026-07-11，`截圖結果/case6-sgr-forms.ps1.png`）：
文件／issues 情報對使用者現行版本過時——全部 SGR 形式正常渲染**：

| row | 形式 | 結果 |
|---|---|---|
| 1 | 無色碼對照 | 純文字 ✓ |
| 2 | 基本 16 色 fg（31/32/34/36） | 全部上色 ✓ |
| 3 | 亮色（92/93/90） | 全部上色 ✓ |
| 4 | 合併碼鏈 `[42;30m` vs 分開碼鏈 `[42m`+`[30m` | **兩者皆正常**（#6466 未重現） |
| 5 | 粗體 `[1m` | 正常 ✓ |
| 6 | 256 色 fg `38;5;196`／bg `48;5;24` | **全部上色 ✓** |
| 7 | truecolor `38;2;255;128;0` | **上色 ✓** |

**裁決（2026-07-11）**：色彩契約**維持現狀**（ansi256／truecolor 雙軌），
不新增 ansi16 軌、不做量化；版本相依風險降為 backlog 級註記。附帶
收穫：case6 為 7 列、無尾隨換行、帶色輸出且逐列正常渲染——同步補強
§3.2 行尾契約與 §3.3 多列結論（帶色情境亦成立），case1／case5 的
選擇性重測不再需要。
