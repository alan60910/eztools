## 一、頂帶高度預算實測數據

| Viewport | 頂帶實際高度 (px) | 佔 viewport % | `max-height` 計算值 (px) | ≤40dvh？ |
|---|---|---|---|---|
| 375×667（mobile） | 266.8 | **40.0%** | 266.8 | ✅ PASS（恰貼邊界，見下方說明） |
| 390×844（mobile） | 265.8 | 31.5% | 337.6 | ✅ PASS |
| 1280×800（desktop 對照） | 223.0 | 27.9% | 320.0 | ✅ PASS |

**375×667 說明**：頂帶內容（標題＋兩組 segmented control＋mock 時鐘 hint＋3
列終端預覽）的自然高度已達到或略超過 `40dvh` 預算，被 `.preview-section`
的 `overflow:hidden`（style.css:1071）精準裁切在預算內——這正是 T4.1
「終端框內部捲動」契約（style.css:1214 `.preview-terminal { flex:1 1 auto }`
＋自身 `overflow-y`）設計上該發生的行為：截圖（`t44-mobile-375x667.png`）
可見終端框僅顯示前 2 列（model/cwd、cost/duration），第 3 列
（context-used/rate-5h）需終端框內部捲動才看得到——**此為既有設計契約
運作正常的證據，非本次新發現的缺陷**（PLAN §D4 A-1「內部（終端框）縱向
捲動」明文允許）。

## 二、「下方至少一個完整列群組可見」——實測 FAIL＋根因

| Viewport | 版面模式 | 目錄欄高度 (px) | 第一列群組 top→bottom (px) | 列群組高度 (px) | 完整可見？ |
|---|---|---|---|---|---|
| 375×667 | 單欄堆疊（`main` 非 grid，<1100px） | 2460.7 | 3374.6 → 4622.6 | 1247.9 | ❌ FAIL（viewport 僅 667px，缺口 ~3955px） |
| 390×844 | 單欄堆疊 | 2460.7 | 3374.6 → 4622.5 | 1247.9 | ❌ FAIL（viewport 僅 844px，缺口 ~3778px） |
| 1280×800（對照） | 雙欄並列（`main` 為 grid，≥1100px，style.css:1413-1422） | 2539.1 | 645.1 → 1628.3 | 983.1 | ❌ FAIL（viewport 僅 800px，缺口 ~828px） |

**根因一（結構性、影響最大）——單欄堆疊時目錄搶佔 DOM 序在前**：
`<1100px` 時 `main` 退化為單欄 block 堆疊（`mainIsGrid: false` 實測確認），
DOM 序為 `.builder-columns__catalog`（內含「全域設定」`#global-section`＋
四類共 30 段目錄，index.html:252-457）**先於**
`.builder-columns__selected`（列群組容器，index.html:491）。目錄欄本身高
達 2460.7px（30 段常駐項＋4 個分類標題），使「已選擇」欄／第一個列群組
被推到 y≈3209/3374——**與 viewport 高度差了一個數量級**，並非「剛好差一點
點」的邊界情況。

**根因二（次要、任何寬度皆存在）——單一列群組本身即高於一般行動 viewport**：
即使在 ≥1100px 雙欄並列（目錄／已選擇 align-items:start 同列起跑，
style.css:1421 `align-items: start`）、第一個列群組 top 已貼近頂帶下緣
（645px，對照 mobile 的 3374px 好上一個數量級），該列群組自身高度仍達
983.1px（2 段 × 每段完整編輯列 428.6px＋列群組 header／分隔符控件）——
**單一 segment 完整編輯列**（列位／顯示文字／前綴／顯示樣式／顏色／fg
覆寫／閾值／bar 八欄，T2.2 新增預設值標示後更長）本身量測得 **428.6px
（桌面寬度）／520.6px（375px 窄寬度，欄位換行更多）**。這代表：**任何
config 只要一列有 ≥2 段，「該列完整可見」這個字面驗收條件在任何手機尺寸、
甚至 1280×800 桌面對照組下都不可能不捲動達成**——並非本次三個測試尺寸
的巧合，是目前 segment 編輯列 UI 密度的必然結果。

`t44-measure-raw.json`（同目錄）存有完整原始數據（含 `globalSectionRect`／
`selectedTop`／`firstSegmentRowHeight`／`segmentRowsInFirstGroup` 等佐證
欄位）。

### 建議修法（不自行修，供協調者／PLAN 決策）

1. **（建議優先）驗收條件本身需修訂**：PLAN §D4 A-1「下方工作區至少一個
   完整列群組可見」在目前 segment 編輯列 UI 密度下並非可達成的硬指標
   （根因二已證明——與螢幕尺寸無關）。建議改為較寬鬆、可達成的目視驗收
   句，例如「頂帶下方立即可見『已選擇』欄的標題與第一個列群組的 header
   列（分隔符控件／刪除鈕），使用者無需目錄捲動即可辨識已進入正確區塊」
   ——不要求整段完整可見，捲動存取完整編輯列視為預期互動（terminal 內部
   捲動的姊妹契約）。此修訂僅動 PLAN 文字，不影響任何既有測試／golden。
2. **（可選、僅解根因一）單欄堆疊時「已選擇」欄視覺順序提前於目錄欄**：
   `<1100px` 斷點下用 CSS `order`（flex/grid 皆可加 `order` 於既有 block
   容器改 `display:flex; flex-direction:column` 或直接調整二容器書寫序＋
   `order`）讓 `.builder-columns__selected` 排在 `.builder-columns__catalog`
   之前，使行動裝置使用者一進頁面（捲過頂帶）先看到自己已選擇的列，目錄
   （30 段常駐清單）改置於其後。此舉可將「缺口」從 ~3800px 級降到接近
   desktop 對照組的 ~800px 級（根因一解決），但**不會解決根因二**——單
   一列群組本身 983px／1247px 的高度仍會讓「完整可見」失敗，除非同時採
   納建議 1 放寬驗收句。兩者建議搭配採用，單獨做建議 2 不足以達標。
   風險：DOM 序與視覺序不一致對螢幕報讀機／Tab 序有 a11y 含意，需另評估
   `tabindex`／地標播報順序是否受影響（本 spike 未評估，留待若採納此案
   時的實作任務自行驗證）。
3. 不建議在本 sprint 內壓縮 segment 編輯列高度（八欄位＋T2.2 預設值標示
   為 M1/M2 已交付的核心可用性訴求，壓縮版面屬另一次 UX 決策、非本
   spike 範圍）。

## 四、`<dialog>` 相容矩陣

### Edge/Chromium 實測（本機真實瀏覽器，非 jsdom fallback 分支）

| 測項 | 結果 |
|---|---|
| `showModal()` 開啟 | PASS——`open` 屬性出現、`:modal` 偽類命中（`matches(':modal')===true`，證明走真模態路徑非 jsdom fallback） |
| 開啟時焦點 | PASS——`document.activeElement` 為 `#copy-bash`（dialog 內第一個可聚焦元素，與 `focusFirstFocusable` 設計一致） |
| **Esc**（真實 `Input.dispatchKeyEvent` 鍵盤事件，非 JS 合成 close()） | PASS——原生 modal dialog 的 cancel→close 語意觸發，`open` 屬性消失＋焦點**顯式**還原至 `#output-dialog-open`（證明 `wireOutputDialog` 的 `close` 事件監聽器確實接住了瀏覽器原生觸發的關閉、非僅接住自家 `closeOutputDialog()` 呼叫） |
| Backdrop click（真實滑鼠事件點擊視窗角落，非 dialog 內容區） | PASS——`open` 屬性消失＋焦點還原至 `#output-dialog-open` |
| 顯式「關閉」鈕 | PASS——同上 |

四項关闭來源皆收斂到同一段焦點還原邏輯，與 main.ts:2805-2814
`wireOutputDialog()` 的設計意圖（單一 `close` 事件出口）完全吻合，**真實
瀏覽器行為與 T4.2 既有 14 案 jsdom 案的判定一致**，T4.2 report 決策 2/3
（fallback 特徵偵測、close 事件唯一出口）在真瀏覽器下獲得實測佐證。

### 文件面相容矩陣（未裝新瀏覽器，引 MDN／caniuse 既有知識，標注為文件面）

| 瀏覽器 | `<dialog>` 基礎支援 | `showModal()`／`::backdrop`／原生 Esc-cancel | 本專案 fallback 是否觸發 |
|---|---|---|---|
| Chromium（Chrome/Edge） | 早（Chrome 37, 2014） | 早（Chrome 37 起即含 showModal） | 否——走 `showModal()` 正常路徑（本次實測確認） |
| Firefox | 98 起完整支援（2022-03） | 98 起 | Firefox <98：走 fallback（`open` 屬性＋手動 dispatch close） |
| Safari（含 iOS Safari） | **15.4 起**（2022-03）**才有**——15.4 之前**完全無** `<dialog>` 實作（非部分支援，是零支援：無 UA stylesheet 的 `dialog:not([open]){display:none}` 規則，也無 `<dialog>` 的 parsing/CSS 特殊處理） | 15.4 起 | Safari/iOS Safari <15.4：走 fallback |

**Fallback 決策建議句（供協調者回寫 PLAN）**：

> 既有 `typeof el.showModal === 'function'` 特徵偵測 fallback（main.ts
> `openOutputDialog`/`closeOutputDialog`，T4.2 已實作）已滿足 Firefox <98／
> Safari <15.4 等無 `<dialog>` 實作瀏覽器的「不炸＋可操作＋可關閉」最低
>需求（含本 task 新增的顯式關閉鈕，彌補非模態 dialog 無 Esc 語意的缺口），
> **建議額外補一行防禦性 CSS**
> `dialog.output-dialog:not([open]) { display: none; }`
> （style.css:1272 區塊目前缺此規則，僅依賴瀏覽器原生 UA stylesheet 提供
> 同款規則——但**完全不支援 `<dialog>` 的瀏覽器正好沒有這條原生規則**，
> 若不補此行，這類瀏覽器會在使用者按下「產出腳本」之前就讓已授權樣式
> 化的 `<dialog>` 內容以一般 block 元素之姿常駐可見，形成未預期的頁面
> 雜訊）；鑑於 iOS Safari 15.4 距今（2026-07-17）已逾 4 年，此為低成本
> 防禦性收尾而非急迫修復。

## 結論

- 頂帶高度預算（G4/D4 A-1 前半）：**達標，PASS**。
- 列群組完整可見（G4/D4 A-1 後半）：**未達標，FAIL**（三尺寸皆 FAIL，含
  桌面對照組）——根因與建議修法見「二」節，**BLOCKED-FINDING，未自行修**。
- dialog 相容矩陣：**PASS**（Edge/Chromium 實測五項全過；Firefox/Safari
  文件面矩陣＋fallback 決策句已交付，`dialog.output-dialog:not([open])`
  CSS 缺口為本次新發現、低成本、非阻斷性的補充建議）。

BLOCKED-FINDING: 「頂帶下方至少一個完整列群組可見」驗收條件於 375×667／
390×844／1280×800（含 PLAN 指定桌面對照組）三尺寸實測皆未達標，根因為
（1）<1100px 單欄堆疊時 30 段目錄欄（2460.7px）DOM 序先於「已選擇」欄，
及（2）單一 segment 完整編輯列本身高達 428.6–520.6px，2 段一列即達
983–1248px、任何螢幕尺寸皆無法整段免捲動可見。建議修法（PLAN 驗收句
放寬 為主、CSS order 調整 DOM 視覺序為輔）已詳列於「二」節，未自行修改
任何生產碼。
