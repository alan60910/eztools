## 實作內容

1. **型別**：`BuilderConfig.rowSeparators?: (SeparatorConfig | null)[]`，落點緊鄰
   `separator`（config.ts:104-125），附完整語意文件（索引基準、null＝繼承全域、
   powerline 保值不清除、正規形定義）。

2. **`sanitizeRowSeparator(raw): SeparatorConfig | null`**（config.ts:274-285）：
   與 `sanitizeSeparator` **平行實作、各自獨立的失敗出口**——不呼叫
   `sanitizeSeparator` 也不複用其回傳形。`null`／非物件／缺 `value`／未知
   `preset` 值／`custom` 過 `validateCustomText` 失敗／未知 `kind` 一律回
   `null`；僅結構完整者委派既有驗證核心（`SEPARATOR_PRESETS` 白名單、
   `validateCustomText`）。

3. **`sanitizeRowSeparators(raw, catalog)` 陣列級清洗**（config.ts:296-307）：
   非陣列 → `undefined`（欄位缺席）；`raw.slice(0, catalog.ids.length)` 做長度
   clamp（DoS 防禦，比照 `sanitizeRow` 對 `row:999999999` 的上界精神，但這裡
   clamp 的是**陣列長度**而非索引值，上界＝目錄段數本身，非段數−1）；逐元素
   委派 `sanitizeRowSeparator`；clamp 後修剪尾端連續 `null`；修剪後全 `null`／
   空陣列 → `undefined`（省略欄位，正規形＝「全繼承」不留冗餘陣列）。

4. **`sanitizeConfig` 重構為核心＋擴充兩層**（config.ts:376-394）：
   - 新增 `sanitizeConfigCore`：承接原 `sanitizeConfig` 除 `rowSeparators`
     外的全部欄位清洗邏輯（`version`／`mode`／`separator`／`lastArrowCap`／
     `powerlineArrow`／`segments`），回傳型別 `Omit<BuilderConfig,
     'rowSeparators'>`。
   - `sanitizeConfig` = `sanitizeConfigCore` + `sanitizeRowSeparators`（僅
     `rowSeparators` 非 `undefined` 時併入）。

5. **`migrateConfig`（v1→v2）改呼叫 `sanitizeConfigCore` 而非 `sanitizeConfig`**
   （config.ts:410）：這是滿足「migrateConfig v1 分支不得產生此欄」契約的關鍵
   決策——不是「產生後再過濾掉」，而是從源頭上讓 v1 遷移路徑完全不知道
   `rowSeparators` 這個 v2 專屬概念，即使 raw（v1 存檔）湊巧夾帶合法
   `rowSeparators` 資料，遷移產出也恆不含此欄（已有測試案覆蓋此情境）。
   此設計避免了解構丟棄未用變數的彆扭寫法，且更直接對應 PLAN 的語意（v1
   無「config 正規化後啟用列位」這個概念可依附）。

6. 未改動：`__golden__/`、`main.ts`、`resolve.ts`、`emit-*.ts`（未觸碰，遵守
   禁改範圍）；`CONFIG_VERSION` 維持 2。

## 關鍵決策
- **不複用 `sanitizeSeparator` 的 return 形**：`sanitizeRowSeparator` 是全新
  平行函式，失敗出口回 `null` 而非 `defaultSeparator()`，避免把畸形覆寫污染
  成「明示選 `'|'`」的假訊號。
- **陣列長度 clamp 上界 = `catalog.ids.length`（非 −1）**：這是長度上界，不是
  索引上界，與 `sanitizeRow`（索引 clamp 至 `length−1`）語意不同但同源精神
  （防手改存檔塞巨陣列）。
- **`sanitizeConfigCore` 抽取**：讓 `migrateConfig` 對 `rowSeparators` 保持
  「無知」而非「知道後丟棄」，源頭杜絕而非事後過濾，程式碼與契約意圖直接對應。
- **尾端 null 修剪與 mode 無關**：修剪是陣列正規形的一部分，不因 `mode` 為
  `powerline` 而略過——`rowSeparators[i] ?? config.separator` 消費模式下，
  陣列末端缺席（`undefined`）與顯式 `null` 效果相同，故裁剪安全。測試案
  「mode 為 powerline 時欄位保值不清除」特意用**非尾端** `null` 以避免與修剪
  規則的斷言衝突（此為撰寫測試時發現並修正的一個小陷阱，非實作缺陷——
  首版測試誤判了 clamp／trim 交互，已修正）。
