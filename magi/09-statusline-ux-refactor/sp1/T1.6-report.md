### 3. 端到端「整列執行期死亡＋後列覆寫」（`pipeline.integration.test.ts`）

`resolve.test.ts`「rowSeparators 啟用位映射」describe 的「整列執行期死亡
對位案」（T1.3 交付，node 單元層級）已釘住 `resolve()` 對
`enabledRowOrder`（config 正規化後啟用列位）與 `renderRowOrder`（執行期
存活列緊縮序）分岔時不得混淆；本任務補其**端到端 byte-exact 覆蓋**
（真跑 bash＋jq／PowerShell 5.1，沿 `describe.skipIf(!(BASH.ok && PS1.ok))`
既有體制）：

- 三列 plain config：啟用位 0（`session-name`＋`vim-mode`，皆 `hide`
  政策）於 `early-null` mock 情境（欄位缺席）整列執行期死亡；啟用位 1
  （`context-used`＋`context-remaining`，`dash` 政策，顯 `NA_TEXT`）
  `rowSeparators[1]=null` 顯式繼承全域 `'|'`；啟用位 2（`git-branch`＋
  `cost`）`rowSeparators[2]` 覆寫 preset `'›'`，亦為存活輸出的**最後一
  列**。若 emit-bash／emit-ps1 誤以「存活列緊縮序」索引 `rowSeparators`
  （如直接以迴圈變數取代啟用位），存活輸出最後一列會誤取啟用位 1 的
  `null`（退全域 `'|'`）而非啟用位 2 的 `'›'`——本案可揪出。
- `git-branch` 為真 shell-out 段：沿既有「D1 gating 真執行覆蓋」區塊的

  `early-null` mock 情境的 `shell['git-branch']='main'`，確保真執行與
  oracle 同一態、byte-exact 才有意義。
- 前置自檢：`toAnsi(resolve(...))` oracle 恰兩列，字面
  `` `${NA_TEXT}|${NA_TEXT}\nmain›$0.0000` ``；bash／ps1 真跑 stdout 與

## 關鍵決策

1. **兩份 canonical config「equivalent 非逐字」原則延續**：ps1 側新案
   不 import 或複製 bash 側 config 物件，改在 `.mjs`／`.test.ts` 各自寫一
   份結構等價（同段序、同覆寫語意）但欄位風格各自獨立（如 icon 預設值
   不同）的版本——沿 T4.6（`full-30-plain` 等）已立下的慣例，維持「兩處
   canonical 各自獨立事實來源、golden 測試互為漂移守門」的既有架構。
2. **多列新案刻意「最小 diff」設計**：`multirow-plain-rowseps` 的段組合
   與 row 分佈逐欄照抄既有 `multirow-plain`（僅新增 `rowSeparators`），
   而非另起爐灶的全新段組合——理由：golden diff／code review 時可直接
   對照兩案差異即為「加了 rowSeparators 後的行為」，不必同時消化「新段
   組合是否正確」與「rowSeparators 是否正確」兩件事。
3. **顯式尾端 `null`（非陣列過短之缺項）**：`multirow-plain-rowseps` 的
   `rowSeparators` 刻意寫成 `[null, {...}, null]`（三元素，含尾端顯式
   `null`）而非 `[null, {...}]`（兩元素，讓陣列過短由 `?? config.separator`
   的越界 `undefined` 兜底）——因為本檔為 raw `BuilderConfig` 直接餵
   `emitBash`／`emitPs1`（不經 `sanitizeConfig` 之「序列化前修剪尾端
   null」正規化），兩種來源（「顯式 null」vs.「陣列過短」）在此有機會
   各自獨立覆蓋，之前 T1.4/T1.5 單元測試已覆蓋「陣列過短」（見
   `emit-bash.test.ts`「陣列過短（越界索引→undefined）」精神的既有案），
   本案刻意選「顯式尾端 null」補上另一半。
4. **「8 檔」明列以硬編字面清單斷言，而非僅斷言 count**：`toEqual` 比對
   排序後的名稱陣列（非僅 `.length`）——若未來任何既有 powerline case
   改名／新增／刪除，本斷言會因清單不符而變紅，逼審查者同步更新本檔與
   `T1.6-report.md` 對應段落，而非讓「筆數剛好對上」的巧合掩蓋清單本身
   已經漂移的事實。
5. **單列 golden 新案掛 `scenario` 取得免費的 bash 真執行覆蓋**：兩個新
   單列案選用不含 shell-out、不含 threshold 分裂的簡單段組合（`model`／
   `cost`／`duration`／`version`），使其可直接掛 `fullWith()`（FULL 情境
   原樣、無需 mutate）並自動納入 `emit-bash.test.ts` 既有的
   `buildByteExactCombos()` 迴圈，零額外樣板取得端到端覆蓋；ps1 側因該
   檔的真執行案是另一組獨立建構的 combo 函式（非隨 `GOLDENS` 自動生
   效），未強行對稱補齊——golden byte 凍結＋單元結構斷言已足夠覆蓋 ps1
   側這兩案本身的正確性，真正的「多後端端到端」覆蓋交給第 3 節的整列
   死亡案（bash＋ps1 皆真跑）。
